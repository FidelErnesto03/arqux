## PROBLEM
La dependencia pineada codec-cortex==1.0.0rc1 es INCOMPATIBLE con el codigo que la consume y desactiva silenciosamente la capacidad CORTEX de ArqUX. src/arqux/core/state/__init__.py lineas 60-65 importa exclusivamente el nombre de modulo legacy 'cortex.*' (cortex.core.ast, cortex.core.lexer, cortex.core.parser, cortex.core.validator, cortex.crud.selectors, cortex.hcortex.read_renderer). Verificado en venv aislado con 'uv pip install -e .[codec]' (codec-cortex 1.0.0rc1 desde PyPI): 'import cortex' -> ModuleNotFoundError, 'import codec_cortex' -> OK, pero 1.0.0rc1 expone submodulos PLANOS (parser, hcortex, c14n, scalars, slotparser) y no tiene 'codec_cortex.core' ni 'cortex.crud'. Resultado medido: _HAS_CODEC_CORTEX = False. Consecuencias: (1) requires_codec_cortex() lanza RuntimeError y el handler MCP cortex_verify devuelve OUT-ERROR code=MISSING_DEPENDENCY, con lo que la condicion §13 'cortex verify --strict' del gate de BLP-004 no es ejecutable; (2) _project.py linea 38 y _render.py degradan todo archivo de gobernanza al camino legacy (sin manejo de $0); (3) la CI, que instala el pin, corre la suite completa con la capacidad CORTEX desactivada. El gap de deteccion: tests/test_cortex_two_column_conformance.py lineas 50-52 SI tolerate ambos nombres (try 'cortex.core.parser' / except 'codec_cortex.parser'), o sea la suite conoce las dos columnas pero el codigo de producto solo conoce la legacy; como la suite local corre con 0.6.2 en la columna A, ningun test detecta la degradacion. Nota: el pin ya estaba registrado como discrepancia en BLP-001 T-1.2 pero con la lectura incorrecta de 'la candidata es ejecutable pero no esta cableada'; la realidad es que cablear el pin DESACTIVA la verificacion. Fix: hacer que core/state/__init__.py resuelva ambos nombres de modulo y anadir un test que falle si _HAS_CODEC_CORTEX es False con el pin declarado instalado.
